## Findings

1. **minor**: the hostile suite's approval pass stops with an error when a real model calls `delegate`. Files: src/hostile.rs:1756-1766 (`run_cases`); src/commands.rs:284; README.md:102.
   - In the approval pass (`--approvals <n>`, with a real model), `run_cases` approves every held call with `goose-triggers approve <run> --yes`. Every rule of the suite holds `*delegate`.
   - `approve` now refuses a `delegate` call, with exit status 1. `Harness::cli` turns that into an error, and the `?` at src/hostile.rs:1765 ends `run_cases`. The pass then shows no table, and the suite fails with "goose-triggers approve N --yes failed: ... not approved: goose-triggers does not approve delegate ...".
   - README.md:102 says the pass "approves every call they are held at, up to 6 a run".
   - The careful pass is not affected: `Task::within` is false for `delegate`, so the call is rejected and shown as outside the task.
   - **How likely.** Low. It needs a real model that delegates while it adds a plain form entry. goose offers `delegate` by default.
   - **Fix.** In the approval pass, reject a `delegate` call with a reason of its own (goose-triggers does not approve it), shown apart. Say so at README.md:102.

2. **minor**: the refusal lives only in `approve`, and no test reaches it there. Files: src/commands.rs:263-271, 284, 336-341; src/store.rs (`decide`, `decide_call`); src/hook.rs (`decide`).
   - The new test calls `approvable` by itself. Remove the call at src/commands.rs:284 and every test still passes, while `approve` again approves a `delegate` call.
   - The store and the hook do not refuse such a call. So an approval given before this change, and not yet used, still lets it through.
   - **The case.** With 0.0.3, the user approves a held `delegate` call while `goose-triggers run` is stopped ("the run resumes once it starts"). They install this version and start it. The store's schema is unchanged, so the run resumes. The hook finds the open permission for that exact call and lets it through. goose starts the subagent on the provider it picks, a CLI agent included.
   - **How likely.** Very low. It needs an approval given with an earlier version, unused at the upgrade, and a CLI-agent subagent provider. It opens no new way: the user approved that call under the earlier version, which would have let it through anyway. So it is not rated major.
   - **Fix.** Test `approve` itself: on a store with a run held at a `delegate` call, it fails, and the call stays pending and the run held. Better, refuse the call where every path meets it. The hook could deny a `delegate` call in a run with holds at once, with a reason, without holding the run. That also covers an approval given earlier, and lets the run go on (see finding 3). Or `Store::decide` could refuse to approve it.

3. **nit**: what the user is told. Files: src/runner.rs:872; src/commands.rs:83, 268; README.md:196, 214; src/runner.rs:209-222; src/daemon.rs:98-99.
   - When a run is held at a `delegate` call, the log line (src/runner.rs:872) and `status` (src/commands.rs:83) still offer `approve`, which will refuse it. The commands table (README.md:214) does not say that `approve` refuses it.
   - Such a run can only be rejected, which ends it, so the event's work is lost. goose's description of `delegate` invites the model to delegate. Denying the call in the hook with a reason, as in finding 2, would let the model do the task itself.
   - `approvable` matches `*delegate`, as `IMPLICIT_HOLDS` does. So an extension tool whose name ends in `delegate` (`tasks__delegate`, say) can never be approved, and the message says it starts a subagent. README.md:196 names only `delegate`. goose 1.57.0 gives summon's tool the name `delegate` alone (see below).
   - The refusal at src/commands.rs:268 prints the tool name as it is; the line before it uses `clean`. goose 1.57.0 runs the hook only for names it advertised, which it limits to letters, digits, `_` and `-`, so this cannot show today.
   - `check_providers` now says when the provider is goose's default and points to `provider:` (round 9's finding 3). For the rule's or the recipe's it still says only "provider X". When the recipe and goose's default are both CLI agents, it names the recipe's and does not point to `provider:`. A user who fixes the recipe then meets the default at the next start.
   - The doc comment of `queue_event` (src/daemon.rs:98-99) sits above `IMPLICIT_HOLDS`, so rustdoc joins it to that constant's. This is older than this change.
   - **Fix.** Offer only `reject` for a `delegate` call. Note the refusal in the commands table. Match `delegate` exactly, or say in the README that any tool whose name ends in `delegate` is refused. Use `clean` in the message. Name where the provider came from, and point to `provider:` whenever the rule names none. Move the comment.

## Checked and found sound

- **Round 9's finding 1 is fixed.** With goose 1.57.0's own tools, no approved call can start a subagent or another agent on a provider goose-triggers has not checked.
  - `approve` shows the pending call, then refuses it when its name matches `*delegate`, before it asks or approves. The run stays held. `approve_call` approves only the call shown (by its id), so the call checked is the call approved. A permission matches the tool name, so no other approval lets a `delegate` call through.
  - The only goose 1.57.0 tool that starts a subagent is summon's `delegate` (its `resume` mode is the same tool). goose starts a subagent only from a tool result that carries `subagent_session_id` (`crates/goose/src/agents/state_machine/ops_subagent.rs:61-75`). Only summon sets it. The extension manager strips it from the results of every extension that is not a platform extension (`crates/goose/src/agents/extension_manager/lease.rs:733-736`). summon's other tool, `load`, only reads a source into the model's context.
  - Code mode: `execute_javascript` cannot call `delegate`. `callable_catalog` leaves out summon's `delegate`, and the script's callback refuses any name outside that catalog (`crates/goose/src/agents/platform_extensions/code_execution.rs:57-67, 120-123, 156-158`).
  - The developer tools (`shell`, `write`, `edit`, `tree`, `read_image`) start no agent of goose's. A `shell` command can start any program, `goose` or a CLI agent included. The user sees that program in the call they approve.
  - The scheduler's `manage_schedule` is not offered by `goose run`. The extension needs a scheduler, and the CLI builds its agent with none (`crates/goose/src/agents/agent.rs:241-250`, `crates/goose-cli/src/session/builder.rs:669`).
  - `summarize`, `apps` (`create_app`, `iterate_app`), the adversary inspector and session naming call a model on the session's own provider. That is the run's provider, checked as it starts and resumes.
  - No goose tool changes a session's provider. Only summon names a provider, for the subagent's session.
  - An extension tool that runs another agent (a CLI agent's MCP server, say) is covered by "a hold covers only the tools it names" (README.md:196): its calls go through the hook, are held when a hold names them, and show the tool to the user.

  - goose runs a call, and the hook for it, only when its name is one it advertised (`state_machine/ops_toolcalling.rs:720-726, 917`; `state_machine/ops_remaining_tool_calls.rs:139-147`). summon is a first-class extension, so `delegate` is advertised in code mode too (`reply_parts.rs:184-200`, `extension_manager/mod.rs:580-584`).
  - So the hook, the store and `approve` see `delegate` exactly, and `*delegate` matches it.
