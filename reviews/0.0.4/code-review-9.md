## Findings

1. **major**: a run with holds can reach a CLI-agent provider through a goose subagent. Once the user approves a held `delegate` call, goose starts a subagent on a provider that goose-triggers never checks. This is older than this change; this review found it while checking every provider goose may run a rule's run on. Files: src/runner.rs:158-191 (`providers_goose_may_use`, `check_providers`, `check_provider`); src/daemon.rs:99-104 (`IMPLICIT_HOLDS`), 184-191 (`check_rule`); README.md:30 and 196; goose `crates/goose/src/agents/platform_extensions/summon.rs:1395-1416` (`resolve_provider_config`), 497-500 (the call's `provider` argument), 937-944 and 988-997 (the subagent's provider, checked only to exist, then saved); `crates/goose/src/agents/subagent_handler.rs:65-67`; `crates/goose/src/agents/platform_extensions/mod.rs:128-137`; `crates/goose/src/providers/claude_code.rs:350-360`.
   - **What is wrong.**
     - goose's summon extension is on by default and offers `delegate`. Every rule with holds holds `delegate` too, so a subagent starts only after the user approves that call.
     - The subagent runs in the same goose process and agent. With an API provider its calls go through goose's hooks, and goose-triggers holds them as it holds the run's own. So a user can approve a `delegate` call and still expect the subagent's commands to be held.
     - goose picks the subagent's provider in this order: the `goose_provider` of the recipe named as `source` (a sub-recipe of the run's recipe, or another recipe); the variable `GOOSE_SUBAGENT_PROVIDER` as it is; the call's own `provider` argument; `GOOSE_SUBAGENT_PROVIDER` read through `get_param` (the variable, then goose's config files); and only then the run's own provider. goose checks only that the provider exists.
     - goose-triggers checks none of the first four. Naming the provider on the rule does not help: `--provider` sets only the last.
     - With a CLI-agent provider, the subagent's tools run inside the other agent. `claude-code` runs with `--dangerously-skip-permissions`, since goose-triggers sets `GOOSE_MODE=auto`. goose does not run those tools, so goose's hooks never see them, as README.md:30 says of these providers.
     - README.md:30 says goose-triggers refuses to run rules with holds on those providers. README.md:196 says why `delegate` is held, but not that its subagent may run on another provider.
   - **The case.**
     - goose's `config.yaml` holds `GOOSE_SUBAGENT_PROVIDER: claude-code`, set for the user's own goose sessions. goose's default provider is `anthropic`.
     - A rule holds `shell`, `write`, `edit` and `read_image`, and names `provider: anthropic`. `goose-triggers run` starts: every check passes.
     - An event's text asks the model to hand the summary to a subagent. The model calls `delegate` with `{"instructions": "Summarize the new file into notes.md"}`. The call is held.
     - The input names no provider and reads as the recipe's own task. The user approves it.
     - goose resumes the run and makes the call. The subagent starts on `claude-code`. That agent runs commands and writes files with its own tools. No hold sees them.
     - The same happens with no config change when the recipe's `sub_recipes` list a recipe whose `goose_provider` is a CLI agent and the call names it as `source`. It also happens when the held call carries `"provider": "claude-code"` itself (an injection can ask for it). Then the provider shows in the call, but nothing tells the user what approving it lets through.
   - **How likely.** Low. It needs a run that calls `delegate`, a user who approves the call, and a CLI-agent subagent provider: in goose's config or environment, in a recipe the call names, or in the call. In the first two the user cannot see it at approval. It is rated major because it is a way for a run with holds to reach a CLI-agent provider, as round 8's finding 1 was.
   - **Fix.**
     - At `run`'s start and at each run's start and resume, for a rule with holds, read `GOOSE_SUBAGENT_PROVIDER` as goose does (the variable as it is, then through `get_param` with the merged files) and the `goose_provider` of each sub-recipe the recipe lists. Refuse a CLI agent.
     - Have the hook deny, with a reason, a `delegate` call whose `provider` names a CLI agent, or whose `source` is a recipe goose-triggers has not checked. Or have `approve` refuse such a call.
     - Say in the README that an approved `delegate` starts a subagent, whose calls goose-triggers holds only on a provider for which goose runs the tools.
     - Add tests for each source of the subagent's provider.

2. **minor**: no test holds round 8's findings 1 and 2 fixed where they were fixed. Files: src/runner.rs:163-168 (`providers_goose_may_use`), 111-118 (the `ACTIVE_PROVIDER` branch of `goose_default_provider`), the tests at 927-961.
   - **What is wrong.**
     - Round 8's finding 1 is fixed in `providers_goose_may_use`: it counts goose's default even when the recipe names a provider. The new test calls `check_providers` with lists written by hand. No test calls `providers_goose_may_use`.
     - Put back the old order there (the recipe's, else the default: one provider) and every test still passes. Round 8's case is then let through again.
     - Round 8's finding 2 is fixed in the branch at 111-118: when `ACTIVE_PROVIDER` is not a name, it passes `false` to `provider_in_goose_configs`. The new test calls `provider_in_goose_configs` with `false` directly. Pass `true` in that branch and every test still passes.
     - `goose_default_provider` reads the process environment, so it cannot be tested as written. Round 8 asked for the order to be tested with the variable's value given as an argument.
   - **Fix.** Split the reading of the environment from the logic: a function that takes the values of `GOOSE_PROVIDER` and `ACTIVE_PROVIDER` (each unset or a text) and the files' texts; and `providers_goose_may_use` taking the default as an argument. Test round 8's two cases through them: a rule with no provider, a recipe naming `anthropic` and a default of `cursor-agent` is refused; `ACTIVE_PROVIDER=1` with `active_provider: openai` in one file and `GOOSE_PROVIDER: claude-code` in a later one gives `claude-code`.

3. **nit**: two points of wording. Files: src/runner.rs:171-184 (`check_providers`); README.md:30.
   - When the recipe names no provider and goose's default is a CLI agent, `check_providers` gets one provider and gives the plain message ("provider claude-code hands runs to another agent ... Use a provider for which goose runs the tools"). It does not say that this is goose's default, nor that naming a provider on the rule (`provider:`) is the way out, as README.md:30 advises. This is the usual case for a user whose goose runs on a CLI agent. A user who then names a provider in the recipe gets the other message at the next start. When the recipe and the default name the same CLI agent, the message names only the default.
   - README.md:30 says each run "checks again as it starts". It checks again as it resumes too (`prepare_working_dir`, src/runner.rs:196-208), and that is the check the fallback needs.
   - **Fix.** Say in the message where the provider came from (the rule, the recipe or goose's default), and point to `provider:` whenever goose's default is a CLI agent. In the README, say "as it starts and as it resumes".

## Checked and found sound

- **Round 8's finding 1 is fixed** for the run's own provider (finding 1 above is the subagent's).
  - goose 1.57.0 picks a run's provider in `resolve_provider_and_model`: `--provider`, then the session's saved provider (on a resume only), then the recipe's `settings.goose_provider`, then `get_goose_provider`. `goose run --resume --text` passes no recipe, so a resume never reads the recipe.
  - A first start with the rule's `--provider`: goose uses that provider. If it cannot be built, the run fails: there is no fallback without `--resume`. goose-triggers checks only the rule's provider. They agree.
  - A first start without it: goose uses the recipe's provider, else its default. goose-triggers checks the recipe's as written and the default (`check_provider` through `prepare_working_dir`), and the rendered recipe's (src/runner.rs:479-485).
  - A resume with `--provider`: goose uses only that one, since the fallback needs `--provider` to be absent. goose-triggers passes `--provider` at every start and resume when the run names one (src/runner.rs:255-257), and checks only it.
  - A resume without it: goose uses the session's saved provider, else its default. When the saved one cannot be built for want of a setting, it uses its default. The saved provider is the one of the run's first start, checked then. The default is checked again at each resume. The recipe's is checked too, which can only add a refusal.
  - goose's other uses of a fallback for a run (`provider_name_for` for a session with no saved provider, `restore_provider_from_session`) also take `get_goose_provider`.
  - `run`'s start check (`check_rule`) builds the same list from the rule and the recipe.
  - The selftest and the hostile suite set `GOOSE_PROVIDER` for the daemon, so the default they see is the provider they use. The selftest's failing rule names its own provider.
- **Round 8's finding 2 is fixed** (finding 2 above aside).
  - `GOOSE_PROVIDER` is taken whatever it holds, the empty text included, as `get_active_provider` takes it. A value that is not UTF-8 is passed over by both, and both go on to `active_provider`.
  - `ACTIVE_PROVIDER` unset or not UTF-8: the files' `active_provider`, then their `GOOSE_PROVIDER`. A name (a JSON string, or text that is not a boolean or a finite number) is taken as it is, untrimmed. Any other value: only the files' `GOOSE_PROVIDER`. This is `get_param` with `parse_env_value`.
  - `inf`, `NaN` and the empty text are names in both, since `Number::from_f64` refuses a number that is not finite. Every text that parses as an `i64` also parses as a finite `f64`.
  - In the files, each key comes from the last file that has it, whatever its value, as `merge_config_values` replaces a top-level key. A value that is not a string (null, a number) is passed over and the next key is read, as `get_param::<String>` fails on it. The read migrations touch only `extensions`.
  - A file that is missing, unreadable or not YAML is skipped by both. A file whose top is not a mapping gives no keys in either.
  - The files are goose's own, in goose's order: `/etc/goose/config.yaml`, the files in `GOOSE_ADDITIONAL_CONFIG_FILES` split as goose splits them, then `config.yaml` in goose's config folder (`GOOSE_PATH_ROOT/config` when that is absolute, else the XDG folder).
  - goose gets goose-triggers' own environment, with `GOOSE_MODE`, `GOOSE_SLASH_COMMANDS_ENABLED` and goose-triggers' two variables added and the webhook secret's variable removed. So goose reads the same provider variables that goose-triggers checks.
  - goose's `get_from_registry` matches a provider name exactly, as `is_cli_agent_provider` does.
- **Round 8's finding 3 is fixed.**
  - `is_date` is asserted false for `date "+'" '+` and for `date '+"' "+`. b32bdbe's even-count check took both as the date.
  - Round 7's three commands are in the refused list, each also with the quotes swapped. bash 5.3 runs the `touch` in all six (checked).
  - The double-quoted `echo` of round 7, both unquoted `echo` forms and both here-documents are refused only by `is_date`. With b32bdbe's check they would be approved, so they hold the fix.
  - The swapped double-quoted form is refused by its shape as well: the lexer reads the closing `"` after the first `)`, then `;` and `)` as operators. It adds nothing, and does no harm.
  - `date '+%F` (a quote left open) is asserted false. Only the open-quote check refuses it, so removing that check fails a test.
  - The comment at src/hostile.rs:2996 is right for each of the six.
