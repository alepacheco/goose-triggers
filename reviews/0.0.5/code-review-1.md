## Findings

1. **minor**: the start check gives a placeholder to every parameter, optional ones included, so `run` can refuse a recipe that every event runs. Files: src/recipe.rs:180-188 (`check_readable`), 81-107 (`params_for`), 116-163 (`check_values_stay_text`); goose `crates/goose/src/recipe/build_recipe/mod.rs:109-150` (a value given wins over the default) and 154-177 (`resolve_sub_recipe_path`).
   - **What happens.** At each event, goose-triggers passes only the parameters the event has (`params_for`). A parameter with a default that no event fills keeps its default in both renders of the structure check. At start, `check_readable` passes `goosetriggersplaceholder` for every non-file parameter. A default that only works as itself then fails at start.
   - **The case.** A recipe declares `file_path` (required) and `helpers` (`requirement: optional`, `default: /home/u/recipes`), and lists `sub_recipes: [{name: summarize, path: "{{ helpers }}/summarize.yaml"}]`. Under 0.0.4 a folder rule on it runs: its events carry `file_path`, `file_name` and `folder`, so `helpers` keeps its default and the sub-recipe exists. Under 0.0.5, `goose run --recipe ... --params helpers=goosetriggersplaceholder --render-recipe` fails with "Sub-recipe file does not exist", and `goose-triggers run` refuses to start. The same happens for any optional value that a word cannot stand in for (a template filter that needs a number, say).
   - **How likely.** Low: it needs an optional parameter used outside plain text. But a config that started under 0.0.4 stops starting after the upgrade, which no deliverable meant.
   - **Fix.** Give placeholders only to the parameters a minimal event must fill (`p.needed && !p.file`), and let goose use the defaults for the rest. Add a unit-level case with an optional parameter.

2. **minor**: a recipe that declares a file parameter skips the start check entirely, so deliverable 7 is done only in part, and README.md:216 overstates it. Files: src/recipe.rs:177-179 (`check_readable`), 89-92 and 94-104 (`params_for`); README.md:216 and 222; goose `crates/goose/src/recipe/validate_recipe.rs:654-681` (`validate_optional_parameters`).
   - **What happens.** goose 1.57.0 refuses a file parameter with a default, and an optional parameter without one. So a file parameter in a recipe goose accepts is always required. goose-triggers never fills it: `params_for` fails the event when it carries the field, and lists it as missing when it does not. Such a rule can never run a single event. Yet `check_readable` returns at once for it, without asking goose anything.
   - **The case.** A recipe with no `title` that declares `{key: doc, input_type: file, requirement: required}`. `goose-triggers run` starts with no word. Each event then fails, with "the recipe's parameter doc is a file parameter" or "the recipe needs parameter(s) doc". README.md:216 says a recipe goose cannot read is refused at start, as goose renders it then with a placeholder for each parameter.
   - **How likely.** Low. README.md:222 tells users to declare strings.
   - **Fix.** Refuse at start any recipe that declares a file parameter, with the reason already at src/recipe.rs:90. `check_readable` then needs no early return.

3. **minor**: the check that goose's settings turn the plugin off does not read goose's `plugins` setting as goose reads it, through `get_param`. This is older than this change, but deliverable 9 says the check now follows goose 1.57.0's reading. Files: src/plugin.rs:134-147 (`disabled_in_config`), 174-192 (`preflight`); goose `crates/goose/src/plugins/discovery.rs:123-152` (`filter_by_config`, which reads `config.get_param("plugins")` at 125); `crates/goose/src/config/base.rs:773-795` (`get_param`), 709-735 (`parse_env_value`).
   - **What happens.** `get_param("plugins")` first reads the environment variable `PLUGINS` (the key in capitals) and parses it as JSON. If it is set, goose does not read the config files' `plugins:` at all. When a file's value is a string, goose also parses that string as JSON. goose-triggers reads only the files' `plugins:` maps.
   - **The case.** `goose-triggers run` is started with `PLUGINS='{"<working folder>/.agents/plugins/goose-triggers":{"enabled":false}}'` in its environment, which goose inherits. goose drops the plugin. goose-triggers starts, and so does each run. No hook runs, so the run's first held call (a `shell` command, say) runs. Only then does goose-triggers see a tool its hook never saw and stop the run (README.md:20 and 272). The same happens with `plugins:` written in `config.yaml` as a quoted JSON string. The other way round, a `PLUGINS` variable with any other value makes goose ignore every file's `plugins:`, so goose-triggers may refuse a start that goose would allow. That is safe.
   - **How likely.** Very low: it needs a variable set on purpose or an odd quoting. The effect is one held call let through.
   - **Fix.** Read `PLUGINS` first, as `parse_env_value` does, and when it is set, use only it. Parse a string `plugins:` value as JSON. Add a unit test for each.

4. **minor**: several behaviours this change adds have no test. Files: src/main.rs:95-111 and 118-130; src/hostile.rs:2244-2317 (`provider_answers`); src/daemon.rs:187-196; src/commands.rs:68-76; src/plugin.rs:176.
   - No test checks that `-c` with `selftest` or `hostile-suite`, `--approvals 11`, `--run-minutes 0` or `--holds ''` exit 2. A `Cli::try_parse_from` test would cover the clap parts. The `-c` refusal is not a clap rule, so it needs its own small function or a run of the binary.
   - The provider check before the first pass runs in no test and in no CI job: CI runs the suite with the scripted model, where it returns at once. Its success path can be run with the scripted model server as an `openai` provider; its failure path with a key the server refuses, or a model it does not have, which fails fast.
   - No test covers the start warning for a rule with no provider anywhere. The decision could be a function of the rule's, the recipe's and goose's default provider.
   - No test covers `status` showing a rejected run's call, or `preflight` keying goose's config by the canonical working folder (one reached through a symlink).
   - **How likely.** A later change can undo any of these without a test failing.
   - **Fix.** Add these tests.

5. **nit**: README.md:59-71 lists what the selftest checks, "in order", and does not list its new check: `goose-triggers run` refuses a rule whose recipe goose cannot read (src/selftest.rs:767-806). Fix: add it to the list.

6. **nit**: `-c` is a global option (src/main.rs:32-34), so `selftest --help` and `hostile-suite --help` still list it, with no word that those two refuse it. Fix: add "(not for selftest or hostile-suite)" to its help line.

7. **nit**: `goose-triggers run` now runs one goose render per rule, one after another, before its webhook listener starts (src/daemon.rs:285-292 and 335; each render may take up to 60 s, src/recipe.rs:230). The selftest's and the suite's harness waits 20 s for the listener to answer (src/selftest.rs:198). Each pass of the suite has 16 rules, one per case, so 16 renders before the listener. On a slow or busy machine (the README's real-model runs on CPU, say) the suite may fail with "the webhook listener" not answering though nothing is wrong. Fix: render the rules at once on threads, or have the harness wait longer.

8. **nit**: when the provider check fails, it shows goose's stderr if it holds any text, else its stdout (src/hostile.rs:2300-2309). goose prints some failures on stdout (`tests/goose-output/no-provider.stdout`, `unknown-provider.stdout`), so any other line on stderr would hide goose's reason. `render` shows both (src/recipe.rs:277-281). Fix: show both, as `render` does.

9. **nit**: three small points of the suite's and the selftest's output.
   - A run's failure reason in the table (`end_of`, src/hostile.rs:1969-1980) and in the summary's "Runs that failed" (src/hostile.rs:2484-2490) is not passed through `shown`. A reason that names a file in the pass's folder (the runner's "... holds other goose plugins", say) prints the full temporary path, not `<suite>`.
   - "none seen (no run got as far as the model)" (src/hostile.rs:2515) gives a cause the suite does not know. With a real model the list comes from goose's output (`advertised_tools`, src/hostile.rs:1548). A goose that stops writing it gives the same line after runs that did reach the model. "none seen in the runs' output" would be exact.
   - `selftest --keep` removes its folder when goose does not run (src/selftest.rs:924-928), while the suite keeps it with `--keep` (src/hostile.rs:2132-2140). README.md:73 says `--keep` keeps it. Nothing is lost, as nothing ran, but the two commands differ.

## Checked and fine

- **Webhook (deliverable 8).** `route` (src/webhook.rs:59-92) answers `/health` and a path outside `/hooks/` as before. It then checks the secret for any path under `/hooks/` before it looks up the rule or the method. `serve_one` calls it before it reads `Transfer-Encoding`, `Content-Length` or `Expect`, so 411, 400 and 413 come only after the secret, and `100 Continue` only after the route passes. `handle` checks again, to the same answer. The log line no longer echoes the sender's path. The tests cover rule names, a folder rule's name, methods, a body over the limit and a chunked body without the secret. README.md:227 matches.
- **Plugin settings (deliverable 9).** Settings files are read in goose's order (the folder's `settings.local.json`, its `settings.json`, then the user's), and the first that names the plugin decides, disabled before enabled within a file. A file goose cannot parse as its settings is passed over, as in `crates/goose/src/plugins/discovery.rs:154-179` and 203-259. The user's file is under `GOOSE_PATH_ROOT` when that is absolute, else under home (226-240). In the config files, the last that has `plugins:` gives the whole map, as `merge_config_values` replaces that key (`crates/goose/src/config/base.rs:320-351`, `load` 529-551); no read migration touches it. The key is the canonical folder, as goose loads hooks for `std::env::current_dir()` (`crates/goose/src/agents/agent.rs:294`). The tests match goose's own tests. README.md:216 names the settings. The one gap is finding 3.
- **Empty plugin folders.** goose takes every folder for a plugin (`discovery.rs:185-201`), but an empty one has no `hooks/hooks.json`, MCP servers or skills, so it adds nothing. A folder that cannot be read still counts as a plugin.
- **The recipe start check (deliverable 7).** `goose run --render-recipe` returns before any session or provider (`crates/goose-cli/src/cli.rs:2246-2252`). goose does not check a value's type against `input_type`. It runs with the webhook secret's variable removed and in the rule's working folder, as each event's render does. The selftest's check needs exit status 1 and goose's reason ("title"). The gaps are findings 1 and 2.
- **No-provider warning (deliverable 6).** It uses `goose_default_provider` unchanged. The refactor into `goose_config_layers` keeps the same files in the same order. It warns and starts.
- **Provider check (deliverable 2).** goose 1.57.0 has `--no-session`, `--no-profile` and `--max-turns`. `--no-profile` loads no extension, nor the plugins' MCP servers (`crates/goose-cli/src/session/builder.rs:575-576` and 591). A provider error becomes an error message (`crates/goose-provider-types/src/conversation/message.rs:1272-1310`), which `headless_run_error` (`crates/goose-cli/src/session/mod.rs:2708-2726`) turns into a failed exit. The check uses the same `GOOSE_PROVIDER`, `GOOSE_MODEL`, `GOOSE_PATH_ROOT` and `GOOSE_DISABLE_KEYRING` as the passes (src/hostile.rs:1457-1468). It is bounded by `--run-minutes`. Ctrl-C or SIGTERM during it kills goose (its own process group, with a parent-death signal) and ends in `finish_interrupted`, with exit status 130 and the folder removed unless `--keep`.
- **Temporary folders (deliverable 4).** The curl, bash and CLI-agent checks come before the folder is made. A failed `goose --version` or provider check removes the folder, or keeps it and says where with `--keep`. README.md:73 and 85 say when each command keeps its folder.
- **Command line (deliverables 1, 3, 5).** `--holds` splits on commas and white space, and refuses an empty list or a bad glob through clap, so it exits 2. `--approvals` takes 0 to 10 and `--run-minutes` 1 to 1440, as clap ranges. `-c` with `selftest` or `hostile-suite` ends through clap's `Error::exit`, so it exits 2. Neither command reads `GOOSE_TRIGGERS_CONFIG`; their harness passes `--config` to each command it runs.
- **Judging and approvals unchanged.** In `src/hostile.rs`, the diff touches only output (`shown`, `brief`, the notes, `minutes`, the tools line), the checks before the first pass, and how `--holds` and the ranges are read. `count`, `toward`, the approval policy, the default holds and the run limit behave as in 0.0.4. The README's statement that the 0.0.4 results hold for 0.0.5 is right.
- **Paths as `<suite>` (deliverable 11).** `replace_path` replaces whole path components only, and the pass's folder before the suite's, so `<suite>/..` names only the suite's own folder. The tests cover a path in the pass's folder, one in the suite's folder, one in the other pass's folder, and one in a folder whose name only starts the same. The legends of the `results/0.0.4` files match, and the one table cell changed (`to <suite>/../notes.md`) is what 0.0.5 would print.
- **Cosmetics (deliverable 10).** `status` shows a rejected run's call: `reject` sets that call's state to `rejected`, both for a held run and for a withdrawn approval (src/store.rs:571-576). "1 minute", the README hint for a missing config file in `load_for_state`, the tools line when no tools were seen, and empty plugin folders are all as asked.
- **Version (deliverable 12).** 0.0.5 is in `Cargo.toml`, `Cargo.lock`, the README's Install block, its `cargo install` tag and its examples URL; `tests/readme.rs` checks the README.
