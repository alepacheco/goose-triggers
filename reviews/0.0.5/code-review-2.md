## The previous round's findings

An event gives at least those values, so the start check is never stricter than the check each event gets. The unit test is at src/recipe.rs:453-471.

README.md:17, 217 and 223 say so. goose 1.57.0 refuses a file parameter with a default (`crates/goose/src/recipe/validate_recipe.rs:659-667`), so no recipe that goose accepts and an event could run is refused.

Otherwise the last file with `plugins:` gives the whole value, as `merge_config_values` replaces the key (320-351). A text value goes through `env_value`, which matches `parse_env_value` step for step (709-734). `disabled_in_config` (src/plugin.rs:174-183) reads the whole map or nothing, as `filter_by_config` does with `unwrap_or_default` (`crates/goose/src/plugins/discovery.rs:124-125`). The tests cover the files, a quoted value, a map goose cannot read, and `PLUGINS`.

## Findings

1. **minor**: the provider check's failure test does not test what its comment says, and one test round 1 asked for is still missing. Files: src/hostile.rs:2816-2824, 2314-2318; src/plugin.rs:210-213.
   - **What happens.** The test runs the check with a provider goose does not have and asserts that the error contains "so the suite sent nothing" and "goose-triggers-selftest-missing". Both strings come from goose-triggers' own message: the provider name is in `through its {provider} provider`. The comment says "refused, in goose's words", but goose's words are never checked. If `said` were empty, or held only one stream again, the test would still pass. So round 1's finding 8 has no test. The test also covers only a goose-side failure (an unknown provider). It covers none of the cases README.md:103 names, where a provider answers with an error (a key it refuses, a model it does not have). Separately, no test checks that `preflight` keys goose's `plugins` setting by the canonical working folder, for a folder reached through a symlink (src/plugin.rs:212). Round 1 asked for that test too.
   - **How likely.** A later change could drop goose's reason from the message, or undo the canonical key, and no test would fail.
   - **Fix.** Assert that the text after "goose said:" contains goose's own "Unknown provider" (as in `tests/goose-output/unknown-provider.stdout`). Add a plugin test where the working folder is a symlink and the `plugins` setting names the real path.

2. **nit**: README.md:74 says "A selftest that fails keeps its folder and says where". When goose does not run, the selftest removes its folder without a word, unless `--keep` is given (src/selftest.rs:926-933). Nothing is lost, since nothing ran. But deliverable 4 asked the README to say when the selftest keeps its folder. Fix: add "(once goose runs)" after "fails", or say that it keeps the folder only with `--keep` when goose does not run.

3. **nit**: two small points.
   - `PATHS_NOTE` (src/hostile.rs:1347) says `<suite>` is a pass's own folder, `holds-off` or `holds-on`. 36c97df now also shows the approval pass's folder as `<suite>` in that pass's table (src/hostile.rs:2557, 2586, `end_of(&root, o)` with `root` = `approvals`). A failed approval-pass run whose reason names a file there prints `<suite>/...` for a folder the note does not name. Fix: name `approvals` in the note too.
   - The comment at src/recipe.rs:165-167 says goose 1.57.0 accepts a file parameter "only as required". It also accepts one as `user_prompt` with no default (`crates/goose/src/recipe/mod.rs:158-162`; `validate_recipe.rs:654-682` refuses only a default on a file parameter, or an optional parameter with no default). The conclusion still holds: `parse` marks such a parameter `needed`, so `params_for` fails every event. Fix: "only with no default".

## Checked and fine

- **Start check (deliverable 7).** `check_rule` calls `check_readable` for every rule, held or not, after the plugin preflight and before the listener binds (src/daemon.rs:174-188, 296-303, 346). `render` runs in the rule's working folder, without the run variable or the webhook secret's variable, within 60 s. The selftest's check copies the selftest config's `goose:` line, passes `--config`, and needs exit status 1, the rule's name and goose's word "title" (src/selftest.rs:767-806). The per-event structure check (`check_values_stay_text`) is unchanged.
- **File parameters.** `params_for` still refuses an event field for a file parameter (src/recipe.rs:89-92). The start refusal is a second check, not the only one.
- **Plugin settings (deliverable 9).** The config files and their order match goose's `Config::default` (`crates/goose/src/config/base.rs:201-207`, `additional_config_paths_from_env` 175-179). `run_read_migrations` does not touch `plugins`. `PLUGINS` is read from goose-triggers' own environment, which goose inherits; the runner does not clear it. An unset, empty or non-UTF-8 `PLUGINS` acts as in goose. The one difference found is on the safe side. A `plugins:` map with a number as a key is read by goose-triggers (serde_json makes the key text) but not by goose, which then turns nothing off. So goose-triggers may refuse a start that goose would allow, never the reverse. The settings-file reading (`disabled_by`) is unchanged and matches `is_enabled` and `read_settings` (`crates/goose/src/plugins/discovery.rs:154-179`, 252-259). README.md:217 matches.
- **Provider check (deliverable 2).** The `env` argument is empty in the suite (src/hostile.rs:2240); only the test sets it. The test's success path points goose's `openai` provider at the scripted model server, which answers any request with text when no recipe mark is present (src/scripted_model.rs:194-240), so goose ends at once. CI runs `cargo test` with goose on PATH (`.github/workflows/ci.yml:78-79`), so the test runs there. Ctrl-C, the time limit and the folder handling are as round 1 found them.
- **Command line (deliverables 1, 3, 5).** `parse_holds` splits on commas and white space and refuses an empty list or a bad glob (`[` is one). The ranges are clap ranges. `requires = "provider"` applies only to a value given on the command line, so the defaults need no provider. `config_not_for_command` is the old condition moved into a function; `main` still ends through clap's `Error::exit`, status 2. `Harness::command` passes `--config` to every command it runs (src/selftest.rs:161-169), so `GOOSE_TRIGGERS_CONFIG` is never read by the selftest's or the suite's commands.
- **Refactors in 36c97df.** `detail` in src/commands.rs is the old `status` match moved out, unchanged. `no_provider` in src/daemon.rs is the old condition, with goose's default still read only when needed.
- **Judging unchanged.** In src/hostile.rs, 36c97df changes only display text (`shown` on failure and export reasons, the tools line) and the provider check's arguments. `count` still decides `held_first`, `acted`, `done` and `held` from the same data. The `ok` checks use only whether the `failed`, `timed_out` and `unread` lists are empty, which `shown` does not change. README.md:109 stays true.
- **Webhook (deliverable 8).** Not changed by 36c97df. `route` checks the secret before the rule, the method, `Transfer-Encoding`, `Content-Length` and `Expect`. Only a path outside `/hooks/` or `/health` is answered without it, and that tells nothing about the rules. The log line names a path only when it is a webhook rule's. README.md:228 matches.
- **Temporary folders (deliverable 4).** The suite's curl and bash checks come before the folder is made. A failed goose or provider check removes the folder, or keeps it and says where with `--keep`. The selftest now does the same.
- **Cosmetics (deliverable 10), paths (deliverable 11), version (deliverable 12).** As round 1 found. `Cargo.toml`, `Cargo.lock` and the README's install commands name 0.0.5, and `tests/readme.rs` checks the README.
