## Findings

1. **minor**: the release binary cannot see users that only the system's name services know, so with no `HOME` it still differs from goose there. Files: src/util.rs:8-39; `.github/workflows/ci.yml:81-84`; README.md:34.
   - **What happens.** The release tarball is a static musl build. musl's `getpwuid_r` reads `/etc/passwd`, then asks nscd if it runs. It does not load the glibc name-service modules (LDAP or SSSD, systemd-homed, systemd's dynamic users). goose's installer gives glibc systems goose's glibc build (`download_cli.sh:217`), whose lookup goes through those modules. Case: an LDAP or SSSD user, not in `/etc/passwd` and with no nscd, starts `goose-triggers run` with no `HOME` (under `env -i`, say). goose finds `/home/<user>`. goose-triggers falls back to `/`. So `preflight` reads `/.config/goose/settings.json` while goose reads `/home/<user>/.config/goose/settings.json`. `goose_config_layers` likewise reads `/.config/goose/config.yaml`. This is round 3's case, with the same result: a `disabledPlugins` entry is missed at start, and the runner's guard stops goose only after the first unheld call has run. The doc comment "found as goose finds it" is then not true. A `cargo install` build links glibc and has no such gap.
   - **How likely.** Very low. It needs no usable `HOME`, a user missing from `/etc/passwd`, and a settings file that turns the plugin off. systemd sets `HOME` for a service that names its `User=`, and cron sets it for every job. root, the usual user of a service with no `User=`, is always in `/etc/passwd`.
   - **Fix.** When `HOME` is unset or empty and `passwd_home()` gives nothing, have `run` refuse to start and ask for `HOME`, instead of using `/`. goose cannot run without a home folder either (`crates/goose/src/config/paths.rs:22-27`, `expect("goose requires a home dir")`), so nothing that works today is lost. At the least, say in the doc comment that the release build reads only `/etc/passwd` and nscd.

2. **nit**: no test covers how `home_dir()` chooses. File: src/util.rs:301-308. The new test only checks that `passwd_home()`, when it gives a folder, gives an absolute one. If someone dropped the `!h.is_empty()` guard at line 12, or the fallback at line 13, every test would still pass. Fix: move the choice into a small function that takes `HOME`'s value and the lookup's result. Then test it with `HOME` unset, empty and set, and with the lookup giving a folder or none.

3. **nit**: the default folders move for a process with no `HOME`. Files: src/main.rs:191-195, src/config.rs:270-272. 0.0.4 used `/.config/goose-triggers` and `/.local/share/goose-triggers` when `HOME` was unset. With an empty `HOME` it used folders relative to where it was started. 0.0.5 uses the user's home. Case: a root system service run without `User=`, which gets no `HOME`, with `-c` and no `state_dir`. After the upgrade it keeps its state in `/root/.local/share/goose-triggers`. `status` no longer shows the runs from before. The change is right: the daemon and a root shell's `approve` and `status` now use the same folder, as goose's folders already did. Fix: one line in the 0.0.5 release notes.

## Checked and fine

- **The unsafe code is sound.** `libc::passwd` holds only pointers and integers, so `mem::zeroed` gives a valid value. The call matches libc's declaration (`libc-0.2.191/src/unix/linux_like/mod.rs:2085-2091`). `buf.len()` is the size in bytes, since `c_char` is one byte. The result pointer starts null. A non-zero return (ERANGE, EIO, EINTR and the rest), "no entry" (zero with a null result) and a null `pw_dir` all give `None` (src/util.rs:33). `pw_dir` then points to a NUL-terminated string inside `buf`, which is not changed while it is read. The bytes are copied into a new `PathBuf` before `buf` is dropped (src/util.rs:36-37). `getpwuid_r` is thread-safe. No signal handler or `pre_exec` closure calls `home_dir`: the closures call only `prctl` (src/runner.rs:332-335, src/recipe.rs:267-270, src/hostile.rs:2283-2286), and the handlers only set a flag or call `_exit`. Nothing in `src/` or `tests/` calls `set_var`.
- **The buffer and ERANGE.** 16 KiB is not retried on ERANGE. It is sixteen times glibc's own suggested size (1024 bytes, from `sysconf(_SC_GETPW_R_SIZE_MAX)`), which is the size dirs-sys gives its buffer (`dirs-sys-0.5.0/src/lib.rs:45-49`). So goose's lookup of the settings file would hit ERANGE long before goose-triggers did. EINTR is not retried either, as in goose's crates.
- **An empty home field.** dirs-sys gives none for it (`dirs-sys-0.5.0/src/lib.rs:62-66`), as `passwd_home` does. std takes it as a valid empty path, so goose would then read its `config.yaml` relative to the working folder, while goose-triggers looks under `/`. That needs a user database entry with an empty home field. It is not worth a change.
- **XDG.** etcetera keeps `XDG_CONFIG_HOME` only when it is absolute, read with `var_os`, else uses `<home>/.config` (`etcetera-0.11.0/src/base_strategy/xdg.rs:169-196`). That is what `config_home()` does (src/util.rs:42-47).
- **The callers.** With `HOME` set and not empty, nothing changes. When it is unset or empty, these now use the user's home where they used `/` or a relative path: `preflight`'s user folder (src/plugin.rs:206-210), `goose_config_dir` and so `goose_config_layers` (src/runner.rs:109-119), the default config file (src/main.rs:191-195), the default state folder (src/config.rs:270-272), and `~` in config paths (src/util.rs:58-71, used at src/config.rs:156, 159, 295, 311 and 324). goose inherits the same `HOME`: the runner only adds variables and removes the webhook secret (src/runner.rs:311-324).
- **The older plugin test.** Only the folder's own settings file can turn the plugin off there, so the `is_err()` at line 298 tests what it means to. The `preflight` wrapper itself is now reached only through the start check (src/daemon.rs:184, src/runner.rs:242). It is a few lines, and round 3 read it.
- **Build.** `0 as libc::c_char` is already used at src/selftest.rs:252, which CI's clippy accepts. `bool::then` and `OsStrExt::from_bytes` are within the MSRV (1.85). `libc` was already a dependency, so `Cargo.toml` and `Cargo.lock` are unchanged.
