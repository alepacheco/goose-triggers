## Findings

1. **nit**: the refusal says the user database names no home folder, but the release binary sees only part of that database. Files: src/daemon.rs:289, README.md:217, src/util.rs:8-9.
   - **Case.** You use the static musl release build. You are an LDAP or SSSD user who is not in `/etc/passwd`, there is no nscd, and you start `goose-triggers run` with no `HOME` (under `env -i`, say). goose's glibc build finds `/home/<user>`. goose-triggers says "the user database names none for this user". But `getent passwd <user>` shows an entry, so the message looks wrong. The doc comment on `home_dir` still says "found as goose finds it".
   - Refusing is still right here: goose-triggers cannot see where goose reads its settings. This is the one realistic setup the refusal stops that started before fc8ab11 (with the weaker check). `Set HOME`, as the message says, fixes it.
   - **How likely.** Very low.
   - **Fix.** Say "no home folder was found for this user". In the doc comment and README, say that the release binary reads only `/etc/passwd` (and nscd).

2. **nit**: the refusal runs after the config is read. So with no home folder, a path under `~` fails first, with a message about a missing file under `/`. Files: src/main.rs:141, src/config.rs:87-99, 295-297, 311-313; src/daemon.rs:280-290.
   - **Case.** The process has no `HOME` and no user database entry (a container user started with a cleared environment). It runs `-c /etc/gt/config.yaml` with `recipe: ~/recipes/triage.yaml`. `resolve_path` turns that into `/recipes/triage.yaml`, and `Config::load` refuses with "rule triage: recipe /recipes/triage.yaml does not exist". With no `-c`, `GOOSE_TRIGGERS_CONFIG` or `XDG_CONFIG_HOME`, the error is "reading the config file /.config/goose-triggers/config.yaml". Either way it still refuses and nothing runs. But you are not told that `HOME` is the cause.
   - **How likely.** Low. It needs the same rare environment as finding 1, plus `~` in the config or the default config path.
   - **Fix.** The check needs no config, so do it in `main` before `Config::load` for `run`, or at the start of `Config::load`.

3. **nit**: the test for whether `GOOSE_PATH_ROOT` counts is now written out three times: src/daemon.rs:286-287, src/plugin.rs:99-100 and src/plugin.rs:207-208. All three agree today, and they match goose (`Paths::validated_path_root`, `crates/goose/src/config/paths.rs:44-46`). A later change to one could miss the others. Fix: add one `goose_path_root() -> Option<PathBuf>` in `src/util.rs` and use it in all three.

## Checked and fine

- **The condition matches goose.** goose moves its folders and the user's plugin settings file under `GOOSE_PATH_ROOT` only when that is absolute. It ignores an empty or relative value (`crates/goose/src/config/paths.rs:8-17, 40-46`; `crates/goose/src/plugins/discovery.rs:226-241`). src/daemon.rs:286-287 tests the same thing. With an absolute root, `preflight`'s user folder and `goose_config_dir` use it (src/plugin.rs:99-100, 207-208). So goose-triggers needs no home folder for the settings it checks. The `/` fallback is then used only for goose-triggers' own default folders, as in 0.0.4.
- **What the refusal can stop.** Without `GOOSE_PATH_ROOT`, goose cannot start without a home folder. goose-cli sets up logging before it reads its arguments (`crates/goose-cli/src/main.rs:20-27`). Logging makes its folder through `Paths::in_state_dir` (`crates/goose/src/logging.rs:55, 116-117`). `Paths` panics with "goose requires a home dir" when etcetera finds no home folder (`crates/goose/src/config/paths.rs:22-27`). etcetera's XDG strategy needs one even when the XDG variables are set (`etcetera-0.11.0/src/base_strategy/xdg.rs:169-171`). So before fc8ab11, the same setup was refused at `goose --version`, with a message that blamed the goose binary. Now the message names the cause. std treats an empty `HOME` as unset, as `home_from` does. Besides finding 1's case, only two rarer setups start goose and are now refused. One is a user database entry with an empty home field: std gives `""`, so goose runs from relative paths, while dirs-sys and `passwd_home` give none. The other is a `goose:` wrapper script that sets `HOME` or `GOOSE_PATH_ROOT` itself. Setting `HOME` fixes both.
- **The selftest and the hostile suite.** Both set `GOOSE_PATH_ROOT` under their temporary folder for every goose-triggers they start (src/selftest.rs:960-964, passed on by `Harness::command` at 161-168; src/hostile.rs:1456-1460). They also set it for `goose --version` and the provider check (src/selftest.rs:920, src/hostile.rs:2236, 2269). That folder is absolute unless `TMPDIR` is relative. So both still start with no home folder, as goose does under them. `tests/selftest.rs` runs the selftest with the test runner's environment.
- **Services and containers.** systemd sets `HOME` for a service that names `User=`, and systemd looks the user up through the system's own name services. A service with no `User=` runs as root, whose entry is in `/etc/passwd`, which the static build reads. cron sets `HOME` for every job. Docker and Podman set `HOME` for the container's user, to `/` when the user has no passwd entry. A `HOME` that is set and not empty is used as it is, and the lookup is not made (src/util.rs:26-29). So none of these is refused.
- **Order and scope.** The refusal comes before the state lock, the store, `goose --version` and `check_rule`'s `preflight`, so nothing is made before it. Everything that reads goose's settings runs in `run` or in the runs it starts, which inherit the same environment: `preflight`, `goose_config_layers`, `goose_default_provider` and `check_providers` (src/daemon.rs:184-205, src/runner.rs:234-242). `status`, `log`, `approve` and `reject` read none of them, so they need no refusal.
- **README.md:217 matches the code.** It refuses when `HOME` is unset or empty, there is no entry (an entry with an empty home field counts as none), and `GOOSE_PATH_ROOT` is unset, empty or relative.
- **A relative `HOME`** is used as it is by `home_from`, dirs-sys and std alike. goose then resolves it from the rule's working folder, and goose-triggers from its own folder. That is not new in fc8ab11, and no shell or service manager sets such a `HOME`. Not worth a change.
- **Build, read only.** `Option::is_some_and` is within the MSRV (1.85). `Path` was already imported in src/daemon.rs. The test's closure `db` captures nothing, so it is `Copy` and can be passed three times. `"/h".into()` becomes an `OsString` through `From<&T>`. `home_from` is private and used outside the test.
