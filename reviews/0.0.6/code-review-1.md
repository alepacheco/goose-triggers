## Findings

1. **minor**: the fix reaches a working folder only when 0.0.6's `goose-triggers run` writes the plugin there, and the README does not say so. Files: src/plugin.rs:29-35 (`hook_command`), 55-72 (`install`); src/daemon.rs:187-197 (`check_rule`, at start); src/runner.rs:242-244 (`prepare_working_dir`, before each run); README.md:18, 32-45, 274.
   - **What happens.** The fix lives in the `hooks.json` that goose-triggers writes into each rule's working folder. A folder written by 0.0.5 or earlier keeps the old command (`|| exit 0`) until a 0.0.6 `goose-triggers run` starts with it as a rule's working folder. A `goose-triggers run` started before the upgrade runs the old code, so it keeps writing the old command until it is restarted. A folder that is no longer any rule's working folder (a rule removed, or its `working_dir` changed) keeps the old plugin for good: nothing removes it. In all these folders goose still blocks every call larger than a pipe, and small ones at random, as `reviews/0.0.5/install-test.md` finding 1 reports.
   - **The case.** A user runs `goose-triggers run` as a service and installs 0.0.6 over 0.0.5 with the Install block, without restarting the service. They open a run's session in its working folder as Use step 5 says. The model's `write` of 70,000 characters is blocked with "the hook did not receive the request payload", as before. README.md:18 says the hook now allows every call in such sessions.
   - **How likely.** Likely for an upgrade without a restart; certain for a folder that is no longer a rule's. No hold is lost: the effect is only that the bug this release fixes is still seen.
   - **Fix.** Say it in the README (Install, or the release notes): after upgrading, restart `goose-triggers run`, which rewrites the plugin in each rule's working folder; in a folder that is no longer a rule's working folder, delete `.agents/plugins/goose-triggers`.

2. **minor**: some promises of this change have no test. Files: src/hook.rs:33-64 (`main_hook`); tests/readme.rs:5-29; README.md:34-45; src/selftest.rs:1003-1013; src/hostile.rs:2129-2141.
   - `main_hook` now reads its whole input before it checks `GOOSE_TRIGGERS_RUN` (deliverable 1). No test runs `goose-triggers hook` outside a run. The plugin tests never reach the binary there, and the in-run test uses a stand-in script. A test can run the built binary (`CARGO_BIN_EXE_goose-triggers hook`) with no `GOOSE_TRIGGERS_RUN` and 1 MiB on stdin, and check that all of it is taken, the exit status is 0 and nothing is printed.
   - Nothing checks that the Install block is joined by `&&` (deliverable 2). `tests/readme.rs` checks only the version. The release workflow runs the block with `bash -e`, which stops at a failed line with or without `&&`. So a later edit that drops one `&&` passes every check. A test can assert that each line of the block but the last ends with `&&`.
   - No test covers `--keep` when goose does not run (deliverable 6): the folder kept and named in the error, or removed without `--keep`. Running the binary with `selftest --goose /bin/false --keep` (and the suite the same way) would cover it.
   - **How likely.** A later change can undo any of these without a test failing.
   - **Fix.** Add these tests.

3. **nit**: when goose does not run, the suite's kept folder is said to hold "goose's own logs of the check", but no check ran. Files: src/hostile.rs:2129-2141; README.md:87. The same error path serves a failed `goose --version` and a failed provider check. After a failed `goose --version` (and always with the scripted model, which has no provider check), the folder holds no such logs. Fix: name the logs only when the provider check ran, or say "goose's own files, if it ran".

4. **nit**: `own_sessions` does not stop on an interrupt. Files: src/selftest.rs:343-405 (`own_sessions`), 576-579; src/util.rs:224-235 (`output_within`). It waits for each goose with `output_within`, which never asks `interrupted()`, and it does not check `interrupted()` before its second session. A SIGINT or SIGTERM sent to the selftest process alone during the first session lets that session finish and starts the second. Then `steps` goes on to `approve` the webhook run, which the daemon may resume, before the next `wait_for` notices. The selftest still ends with status 130 and removes its folder, a few seconds later. The start check at src/selftest.rs:874 has the same pattern. Fix: wait with `wait_output_unless(..., &interrupted)`, and check `interrupted()` before each session.

5. **nit**: two README sentences are a little looser than the code.
   - README.md:66 says the run's session is "opened again as in Use step 5". Use step 5 uses `goose session --resume --session-id <id>`. The selftest uses `goose run --resume --session-id <id> --text ...` (src/selftest.rs:355-364). Both load the plugin from the folder they run in and reach the same `PreToolUse` path in goose (`crates/goose/src/agents/agent.rs:294`, `crates/goose/src/agents/state_machine/ops_toolcalling.rs:126-132`), so the check holds for both. Saying "opened again with `goose run --resume`" would be exact.
   - README.md:75 says a selftest that cannot start "as goose does not run" keeps its folder with `--keep`. With `--goose` naming a path that does not exist, `resolve_goose` refuses before any folder is made (src/selftest.rs:972-984; the suite: src/hostile.rs:2090), so there is none to keep. README.md:87 lists "a bad option" among the suite's refusals with no folder, which may cover it; the selftest's text has no such list. Fix: add "(a `--goose` path that does not exist is refused before any folder is made)".

## Checked and fine

- **The hook outside goose-triggers' runs (deliverable 1).** goose 1.57.0 runs a hook as `sh -c <command>` with the payload piped to its stdin (`crates/goose/src/hooks/mod.rs:1085-1100`). It writes the whole payload, shuts the pipe and drops it, then waits for the hook's output, within the hook's 30 s (1031-1083). A failed write sets `stdin_delivered` false, and `classify_run` (887-895) turns that into a hook failure unless the hook denied. For `PreToolUse` with `on_failure: block`, `apply_verdict` (853-871) then denies the call. The new command, `[ -n "$GOOSE_TRIGGERS_RUN" ] || { cat >/dev/null; exit 0; }; exec ... hook`, reads to the end of input before it exits 0 with nothing on stdout, which `classify_output` (897-947) reads as allow. That holds for any size, and also for `SessionStart` and `UserPromptSubmit`. The brace group is plain POSIX and works under `dash`. A set but empty `GOOSE_TRIGGERS_RUN` is no run, in the shell and now in `main_hook` alike.
- **The hold in goose-triggers' runs.** With `GOOSE_TRIGGERS_RUN` set, the command still `exec`s `goose-triggers hook`, as in 0.0.5. `main_hook` reads the input first and then decides as before. A failed read, a run number that does not parse or a missing `GOOSE_TRIGGERS_DB` still exits 1, so goose denies the call (fail closed). `on_failure: block` is still on `PreToolUse` (src/plugin.rs:47-49). goose reads `on_failure` only for `PreToolUse` (`hooks/mod.rs:999-1007`). The model cannot change goose's own environment, from which each hook is started. No path lets a held call through.
- **The unit tests of the command.** `run_as_goose` runs it as goose does (`sh -c`, `PLUGIN_ROOT` set, stdin piped and closed). Rust ignores SIGPIPE, so with 0.0.5's command the write of 1 MiB fails with a broken pipe and the test fails: it tells the two commands apart. The in-run test checks that a 200,000-byte payload, the argument and the run number reach the binary through `exec`, with a path that needs quoting.
- **The selftest's new check.** goose loads hooks from the folder it starts in, whatever `--no-profile` says (`agent.rs:294`; `builder.rs:561-598`). `--with-builtin developer` gives the developer platform extension (`session/mod.rs:433-458`), so `write` is offered. On `--resume`, goose takes the session's own extensions. `write` resolves a relative path against the session's working folder and writes the content as given (`developer/edit.rs:40-75`, 168-179), so the byte-for-byte comparison is sound. The payload carries 100,000 bytes of content, more than a 64 KiB pipe. The scripted model's new flow comes before the selftest flows, takes `file=` and `size=` from the last user message, and says done once a tool result comes back, so a denied write ends the session and the check fails with goose's "blocked" line. The sessions run with `GOOSE_TRIGGERS_RUN` and `GOOSE_TRIGGERS_DB` removed, under the selftest's `GOOSE_PATH_ROOT`. The run's state and session are checked unchanged. The folder run's session keeps the name goose-triggers gave it, and the later lookup of the failing run's session matches by exact name and folder (src/runner.rs:369-387), so the new sessions do not disturb it. README.md:59-73 lists the check in its place.
- **Install block (deliverable 2).** Every line but the last ends with `&&`, so a failed download or checksum stops it before `tar` or `install`. The block is one list, the last command of the script the release workflow runs, so a failure still fails the job.
- **`null` (deliverable 3).** `fields_from_body` maps `null` to empty text (src/webhook.rs:44). goose takes `key=` with an empty value (`cli.rs:512-517`) and uses a given value as it is (`build_recipe/mod.rs:109-151`). README.md:227 says so.
- **Patterns with `/` (deliverable 4).** `check_rule` refuses them after the glob check (src/config.rs:310), with a reason that says what to do. The test covers it. README.md:209 and 218 say so.
- **No home folder (deliverable 5).** `home_dir` is now an error, and every caller passes it up: the default config path, the default state folder, `~/` paths, goose's config folder and `preflight`. `state_config_path` asks for the default path only when neither `-c` nor `GOOSE_TRIGGERS_CONFIG` names a file, so a named file still serves with no home. `run` still checks first (src/daemon.rs:67-75). The one place that passes the error over, `goose_config_layers`, is reached only by `run`, after that check. README.md:218 matches.
- **Kept folders (deliverable 6).** A failed `goose --version` or provider check with `--keep` keeps the folder and names it after the reason, in the error, in both commands. Without `--keep` the folder is removed. The curl, bash, CLI-agent and option checks come before the folder is made.
- **Empty `--provider` and `--model` (deliverable 7).** `NonEmptyStringValueParser` makes them a clap error (exit 2). The test covers both.
- **Webhook log line (deliverable 8).** Both lines now say "refused (401)" and why. The path is still named only when it is a webhook rule's.
- **Version.** 0.0.6 is in `Cargo.toml`, `Cargo.lock`, the README's Install block, its `cargo install` tag and its examples URL; `tests/readme.rs` checks the README. The statement that the 0.0.4 results hold for 0.0.6 is right: in `src/hostile.rs` the change touches only the kept-folder message.
